# CS Execution Visualizer — Complete Project Specification

## 1. Project Vision

I want to build a modern, interactive **Computer Science Execution & Visualization Platform based on javascript**.

The purpose of this project is to make invisible execution processes visible.

Most programming tools show a developer the source code and final output, but they do not clearly show what happens internally while the program is executing.

This project should bridge that gap.

The core philosophy is:

```text
Source Code / Algorithm
        ↓
Execution
        ↓
Internal State
        ↓
Memory / Data Movement
        ↓
Operations
        ↓
Complexity
        ↓
Interactive Visualization
```

The platform should not merely animate an algorithm.

It should explain:

* What is happening?
* Where is it happening?
* Why is it happening?
* What changed?
* Where is the data stored?
* How does execution move?
* How does memory change?
* How does an error propagate?
* How many operations occurred?
* What is the time complexity?
* What is the space complexity?

The final product should be educational, technically accurate, interactive, performant, and significantly more capable than the reference project described below.

Show concepts such as:

* Global Execution Context
* Function Execution Context
* Local variables
* Parameters
* Scope
* Lexical Environment
* Outer environment/reference
* Return state

```text

├── x = 10
├── add = function
└── result = undefined
```

# 7. Memory State Timeline

The user should be able to move through:


and see how:

* Stack changes
* Heap changes
* Variables change
* References change
* Objects are created
* Objects become unreachable
* Execution contexts change

A state-delta system should highlight what changed between two consecutive execution steps.

# 17. Complexity Calculation

The platform should not simply display:

```text
Binary Search → O(log n)
```

It should explain why.

Example:

```text
Initial search space:
n

After 1 iteration:
n / 2

After 2 iterations:
n / 4

After 3 iterations:
n / 8

...

After k iterations:
n / 2^k
```

Then explain:

```text
n / 2^k = 1

2^k = n

k = log₂(n)

Therefore:

Time Complexity = O(log n)
```

The complexity engine should make the calculation understandable.

# 19. Observed Execution Time vs Theoretical Complexity

This distinction is critical.

Do not represent:

```text
O(n) = X milliseconds
```

as if Big-O directly determines wall-clock time.

Instead show:

```text
Theoretical Complexity
O(n)
```

and separately:

```text
Observed Benchmark

Input size: 10,000
Operations: 10,000
Observed execution: X ms
```

Explain that actual execution time depends on factors such as:

* Hardware
* Runtime
* Browser
* JIT optimization
* Garbage collection
* System load
* Implementation details

The platform may benchmark execution, but must label measurements as observed runtime data.

# 25. Performance Requirements

The new platform should be faster and more responsive than the reference implementation.

Important principles:

* Avoid unnecessary network requests.
* Generate execution traces efficiently.
* Perform playback locally where possible.
* Cache deterministic results when appropriate.
* Avoid unnecessary re-renders.
* Keep visualization state separate from application state.
* Avoid recomputing expensive analysis on every UI update.
* Use incremental/delta state updates where practical.
* Keep large traces manageable.
* Consider Web Workers/background processing for expensive client-side calculations where appropriate.

Do not sacrifice correctness merely for speed.

---

# 26. Architecture Principles

Use a modular architecture.

Separate:

```text
Execution
Trace Generation
Trace Normalization
Trace Analysis
Memory Modeling
Complexity Analysis
Visualization
UI
```

Do not mix business logic directly into visualization components.

Visualization components should consume structured state rather than implementing the execution engine themselves.

# 29. Technical Accuracy

This is a learning tool, so technical accuracy is extremely important.

Do not fake internal behavior merely to create a visually attractive animation.

Whenever the system is showing:

```text
Actual runtime observation
```

make sure it is actually supported by the execution/tracing mechanism.

Whenever the system is showing:

```text
Conceptual model
```

label or structure it appropriately.

For JavaScript specifically, avoid claiming that a visualization represents an exact V8 implementation unless the implementation actually obtains that information from V8.

Use accurate terminology such as:

* Execution Context
* Lexical Environment
* Call Stack
* Heap
* Reference
* Event Loop
* Task Queue
* Microtask Queue
* Garbage Collection
* Stack Unwinding
* Runtime

where appropriate.
